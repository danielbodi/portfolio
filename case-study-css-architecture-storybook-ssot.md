# CSS as the Single Source of Truth

### A scalable CSS architecture (ITCSS + BEM) that feeds a self-updating Storybook design system — with zero token duplication

**Role:** Staff Product Designer — design system architecture, CSS/SCSS system design, Storybook design & implementation
**Product:** FleetBridge — Bridgestone's fleet & tyre operation management platform (Angular / Nx monorepo, multiple apps sharing one UI system)
**Scope:** 254 SCSS files in one shared styles library · ~250 color tokens per theme · 39 story files + 51 MDX docs in Storybook · 2 themes (light/dark) · consumed by web + tablet apps

---

## TL;DR

I designed and built a design system where **the CSS itself is the single source of truth** — not a JSON token file, not a Figma export, not values re-typed into Storybook.

Design tokens live once, as CSS custom properties, in **one SCSS file per foundation** (colors, typography, spacing, animation, elevation, borders, shadows, grid). A strict BEM-based nomenclature makes those tokens *machine-readable*. A small set of TypeScript functions parses the live CSSOM at runtime, retrieves every token, utility class and keyframe, and **feeds Storybook automatically** — swatches, docs tables, and interactive playgrounds all self-populate.

The result: changing a token in one SCSS file updates the apps *and* the design system documentation simultaneously. Documentation cannot drift from production, because documentation is generated *from* production CSS.

---

## 1 · The problem

Design systems typically die one of two deaths:

1. **Duplication** — tokens exist in Figma, in CSS, in a Storybook config, and in developer heads. Every change must be applied 3–4 times; eventually someone forgets one, and the documentation lies.
2. **Static documentation** — foundations pages are screenshots and hardcoded hex values. Designers can't explore them; developers don't trust them.

FleetBridge is a large multi-app Nx monorepo with several Angular applications sharing one visual language, shipped across environments and themes. Manually maintaining a token catalogue for that surface was never going to survive contact with real delivery pressure. So I made a decision early:

> **Write every foundation exactly once — in CSS — and make everything else read from it.**

## 2 · The architecture: BEMIT (ITCSS × BEM)

The shared styles library is organized as an ITCSS "inverted triangle" — eight layers ordered from lowest to highest specificity, so the cascade is architectural rather than accidental:

```text
libs/styles/
├── 1-settings/     Design tokens: CSS custom properties + SCSS maps (one file per foundation)
├── 2-tools/        Mixins & functions — layers 1–2 emit no CSS at all
├── 3-generic/      Resets, normalize, box-sizing
├── 4-elements/     Bare HTML elements (h1, a, button…)
├── 5-objects/      Undecorated layout patterns (.o-flex, .o-layout)
├── 6-components/   UI components (the bulk of the work)
├── 7-utilities/    Generated helper classes & placeholders
└── 8-trumps/       Last-word overrides — incl. Storybook-only chrome, kept inside the same system
```

Every class name follows **BEM with ITCSS namespaces**, declared once as SCSS settings:

```scss
// 1-settings/_settings.core.scss
$bs-objects:    '.o-';   // layout objects        → .o-flex__item--6@md
$bs-utilities:  '%u-';   // utilities as SCSS placeholders
$bs-components: '.c-';   // components
```

A deliberate nuance: **utilities default to SCSS placeholders (`%u-`)**, not classes. Hundreds of elevation/border/shadow utilities are generated by loops (6 elevation contexts × 5 scales × 9 directions × shadow variants ≈ 300 combinations), but they cost **zero bytes** unless a component actually `@extend`s them. Where runtime composition in templates is needed (animations, grid, spacing), they're emitted as real classes instead.

The architecture is enforced, not just documented — Stylelint budgets keep the triangle healthy:

```jsonc
// .stylelintrc (excerpt)
"declaration-no-important": true,     // no specificity wars
"selector-max-specificity": "0,6,3",  // hard ceiling
"max-nesting-depth": 5,
"selector-max-id": 0                  // no IDs, ever
```

## 3 · Nomenclature as an API

The key architectural idea: **BEM is not just hygiene — a strict grammar makes CSS parseable.** I applied BEM's `--` / `__` separators to *custom property names*, giving every token a machine-readable coordinate system.

### Color tokens — a five-level semantic grammar

```text
--color--{category}--{subcategory}__{property}

--color--palette--base__primary            lvl 1  pure palette
--color--generic--theme__cta               lvl 2  themes
--color--generic--background__surface      lvl 3  generic semantics
--color--component--button__background-primary   lvl 4  per-component
--color--status--hover__typo               lvl 5  interaction states
```

Components never touch the palette directly — they consume level 3–5 tokens, which resolve down the chain. And most of those tokens are never written by hand at all: the palette is *generated* from a few base colors, which is its own story (next section).

### Animation tokens — same grammar, second foundation

```text
--animation--{category}__{property}     e.g. --animation--duration__fast: 150ms
animation__{category}--{name}           e.g. @keyframes animation__entry--fade-in
```

Keyframes are *named semantically by category* (entry, exit, movement, loading, attention, status, position) — and most are **generated** by an SCSS loop that pattern-matches token names (`fade-*`, `slide-in-*`, `rotate-*`…), so adding one line in settings produces the keyframe, the mixin support and the utility class automatically.

### Typography — generated classes, semantic aliases

```scss
// .typo__{weight}--{scale}--{line-height} → 4 × 6 × 6 = 144 generated classes
@mixin typography-classes() {
  @each $weight in $_weights {
    @each $scale in $_scales {
      @each $lineHeight in $_lineHeights {
        .typo__#{$weight}--#{$scale}--#{$lineHeight} { … }
      }
    }
  }
}

.typo__h1 { @extend .typo__bold--xxl--xxl; … }   // semantic layer aliases the generic layer
```

The type scale itself is computed *in CSS* from two tokens — a base unit and a major-third ratio (1.25) — so the entire ramp reflows from one variable. Spacing works the same way: an 8-point grid derived from `--spacingUnit`, exposed as `--spacing-0-25 … --spacing-7`.

This grammar is the contract that makes the next two sections possible: a palette that derives itself, and a Storybook that documents itself.

## 4 · The color system: hand-pick 15 colors, compute the rest

The color system is the SSOT philosophy at its purest. There is no 300-row token spreadsheet and no build-time color pipeline: a handful of base colors are declared, and **the browser itself derives the entire palette with modern CSS**.

### Level 1 — the only values a human maintains

[`_settings.colors.scss`](../libs/styles/1-settings/_settings.colors.scss) declares 15 base hues, plus a few fixed anchors (white, black, an off-white mix target, three CTA blues, three dark surfaces):

```scss
--color--palette--base__primary:   rgb(226, 0, 26);
--color--palette--base__secondary: rgb(19, 19, 25);
--color--palette--base__success:   rgb(82, 196, 26);
--color--palette--base__cyan:      rgb(19, 194, 194);
/* …15 hues total. These RGB values are essentially the only hand-picked colors in the system. */
```

### Shade ramps as composable `color-mix()` fragments

The generative trick: shades are not colors — they're **relationships**, stored as the *second half* of a `color-mix()` expression (mix target + percentage) in custom properties:

```scss
// A ramp is just percentages toward a mix target…
--color--secondary__shade-9: var(--color--mix) 10%;    // near-black
--color--secondary__shade-4: var(--color--mix) 90%;
--color--secondary__shade-1: var(--color--mix) 100%;   // near-white

// …and composition happens wherever a semantic token is defined:
--color--generic--background__odd: color-mix(in srgb,
  var(--color--palette--base__secondary),
  var(--color--secondary__shade-2));   // ramp fragment slots in as color₂ + %
```

Two ramps drive everything. The *secondary ramp* (19 steps toward an off-white) produces the *entire neutral scale* — every grey in the product is literally **one near-black, one off-white, and nineteen percentages**. The *scheme ramp* (14 steps toward pure black or white) tints and shades all the accent hues.

### One mixin derives the semantic families

For the 14 accent/status hues, a single `colorScheme()` mixin composes base × ramp into each hue's full semantic set — background, typography, borders, hover and focus states — per theme:

```scss
@include colorScheme(status, error,   light);  // → --color--status--error__background,
@include colorScheme(scheme, cyan,    light);  //   __typo, __border, __border-hover, __border-focus…
@include colorScheme(status, success, dark);   //   dark re-mixes the same base, deeper into the ramp
```

Seven derived tokens per hue in light, five in dark — **≈165 tokens across both themes that nobody wrote and nobody can get out of sync**. Adding a new hue to the system is one base color plus two mixin lines.

### Why the browser computes it, not the build

Sass could bake this math at compile time (`darken()`, `lighten()`); I deliberately kept the derivation in runtime CSS:

- **Change one base color and everything re-derives live** — `color-mix()` resolves at computed-value time from custom properties, so a palette change needs no rebuild and no regeneration step.
- **Dark mode maintains no parallel palette.** Inside `@container root style(--dark-mode: 1)`, tokens simply re-mix the *same* bases against different ramp steps. Light and dark can't drift because they share their inputs.
- **Deployment environments recolor with one token.** Each environment theme file (develop/test/staging/master) just points `--color--environment` at a palette color — the derivation chain does the rest, including its dark-mode variant.
- **Storybook and the runtime see real values.** `getColors()` reads *computed* styles, and the TS color utilities even parse `color-mix()` expressions back into RGB (`calculateColorMixToRgb`), so palette math like avatar color-snapping works on derived colors too.

## 5 · The pipeline: CSS → TypeScript → Storybook

**One file per foundation is the entire maintenance surface.** No token list is ever re-typed. The bridge is a small set of TypeScript functions that treat the browser's CSSOM as a queryable database:

```text
 1-settings/*.scss          compiled CSS           document.styleSheets
 (single source) ──build──▶ custom props ──runtime──▶ TS parsers ──▶ Storybook UI
                                                      getColors()      swatches, docs
                                                      getAnimations()  tables, playgrounds
```

### `collectRootVariables()` + `getColors()` — the core of the system

[`libs/util/src/lib/color-functions.ts`](../libs/util/src/lib/color-functions.ts) walks every same-origin stylesheet, collects custom properties declared on `:root`/`html`/`.fbom`, validates them against the naming grammar, and folds them into a structured object:

```ts
// The nomenclature IS the parser's schema:
if (!/^--color--.+-[^-]+__.*$/.test(varName)) return;

const [path, property] = varName.split('__');          // BEM "element"
const [, , category, subcategory] = path.split('--');  // BEM hierarchy

acc[category][subcategory][`var(${varName})`] =
  getComputedStyle(document.body).getPropertyValue(varName);
```

The output — `{ component: { button: { 'var(--color--component--button__background-primary)': '…' } } }` — is exactly the tree the Storybook color pages render. Categories, subcategories, headings, swatches and values all come from CSS structure. **Add a token in SCSS → it appears in Storybook on next load. Rename it → docs update. Nothing to maintain.**

Because tokens are resolved with `getComputedStyle`, the values shown are the *real, computed* ones — including modern values: the TS layer even parses `color-mix()` expressions back into RGB for palette math.

### The animation foundation — tokens *and* keyframes, parsed live

`animation-functions.ts` goes further: `getAnimations()` harvests every `--animation--*` token by category, and `getKeyframeAnimations()` reads actual `CSSKeyframesRule` names from the stylesheets, grouping them by their semantic prefix (`animation__entry--…`, `animation__loading--…`).

Storybook's own documentation table is generated from this at story-load time:

```ts
// animation.component.stories.ts — ArgTypes ARE the CSS
const meta: Meta<AnimationComponent> = {
  title: 'Foundations/Animation',
  argTypes: generateArgTypes(),   // built by calling getAnimations() against live CSS
  …
};
```

Every duration, easing curve, delay and keyframe documents itself — with generated descriptions and default values — from the single settings file.

### SCSS classes are parsed too, not only tokens

The typography page doesn't list classes; it *discovers* them. It scans stylesheet selectors for the `.typo__` prefix and uses the BEM grammar to classify them:

```ts
const genericClassRegex = /^\.typo__\w+--\w+--\w+$/;   // weight--scale--lineheight
// matches  → "generic" tab   (.typo__bold--xl--xl)
// the rest → "semantic" tab  (.typo__h1, .typo__caption…)
```

The spacing page does the same for `--spacing-*` tokens. One naming convention, one parser pattern, every foundation self-documenting.

## 6 · Foundations as playgrounds, not posters

Static token tables get ignored. Every foundation page in Storybook ships with an **interactive playground** so designers and developers *work* with the system instead of reading about it:

- **Color (Base / Semantic)** — searchable palette rendering every token in **light and dark side-by-side** (the dark swatch simply applies the theme class — same token, both resolutions). Click any swatch → the `var(--color--…)` reference is copied to the clipboard with a toast confirmation. Designers stopped asking "which grey is this?"; developers stopped hardcoding hex.
- **Animation Playground** — a composer: pick a keyframe by category, then duration/easing/delay/iteration/direction, preview it live, and get **three generated, copy-ready outputs**: the SCSS call (`@include animate(fade-in, slow, ease-out…)`), the utility classes (`u-animate u-animate--type-… u-animate--duration-slow`), and the *actual* `@keyframes` rule — extracted live from the stylesheet via CSSOM, never a stale snippet.
- **Elevation & Borders configurators** — dropdown-driven builders (type × scale × direction × shadow) that assemble the exact utility class name and preview it on a live card. The borders builder alone covers ~10 component types with their status variants.
- **Spacing & Shadows playgrounds, Grid gallery** — 18 live grid stories demonstrate the `.o-flex` object system (`o-flex__item--4@lg` responsive suffixes) with argTypes tables documenting every BEM modifier.

The interaction pattern is deliberate and consistent everywhere: **search → preview in both themes → click → copied token/class → paste into code or spec.** The design system is a tool, not a document.

## 7 · The product runtime consumes the same source of truth

The token parsers aren't Storybook-only — the applications themselves use them, which keeps *runtime-generated* UI on-brand:

**User avatars** need a deterministic color per name. A naive string-hash gives ugly, off-brand colors. Instead:

```ts
// avatar directive (production code)
const generatedColor = generateColor(content);              // string → stable hash color
return approximateColor(hexToRgb(generatedColor), colorPalette);
// colorPalette is built by parsing the CSS design tokens via getColors()
// approximateColor snaps to the nearest brand color using Redmean perceptual distance
```

Every generated avatar color is **snapped to the closest color in the design system palette** — and since the palette is read from the CSS custom properties at runtime, a palette change in `_settings.colors.scss` re-brands avatar generation automatically. Text on top picks a light or dark token based on HSL lightness of the resolved background, so contrast holds in both themes.

**Theming** works the same way: dark mode is a single CSS custom property (`--dark-mode`), so every consumer — apps, Storybook, playground swatches — resolves the same tokens with zero JavaScript theme logic.

## 8 · New-generation CSS, in production

I use the modern CSS platform to delete JavaScript, not to decorate.

### Scroll-driven animations in data tables — `animation-timeline: scroll()`

The data tables have sticky columns that need scroll-position-aware shadows (the classic "you can scroll further" affordance). The traditional solution is a scroll listener writing inline styles — jank-prone and off the compositor. Mine is pure CSS:

```scss
// _components.table.scss — shadow appears/disappears as you scroll, no JS
.sticky--left-x:has(+ :not(.sticky--left-x))::after {
  animation: animation__movement--shadow-outside-for-sticky-left linear;
  animation-timeline: scroll(nearest inline);   // driven by the container's horizontal scroll
}
```

The keyframes animate the shadow's width and blur, and the **scroll position itself is the timeline scrubber**. Zero event listeners, runs off the main thread.

The same file leans on selector-level logic that used to require JavaScript:

```scss
.sticky--left-x:has(+ :not(.sticky--left-x))   // "the LAST sticky column" — :has() relational query
.tr > :nth-last-child(2 of .sticky--right-x)   // modern `of S` selector syntax for sticky offsets
```

### Dark mode with container **style queries** — no theme class cascade

Theme state is data (`--dark-mode: 0 | 1`), synced from the OS *and* from an in-page toggle with `:has()` — and consumed via a style container query:

```scss
:where(html) { container-name: root; --dark-mode: 0; }
@media (prefers-color-scheme: dark) { html { --dark-mode: 1; } }
html:has(#color-scheme-dark:checked) { --dark-mode: 1; }

@container root style(--dark-mode: 1) {
  html, .fbom { /* ~100 token overrides — only tokens change, no component styles */ }
}
```

The computed `color-mix()` palette from section 4 is the other half of this platform bet — token derivation, theming and scroll behavior all moved out of JavaScript and build tooling, into declarative CSS.

### Motion accessibility as a system default

`prefers-reduced-motion` is handled globally in the utilities layer: all animation collapses to ~0ms, *except* an allowlist of animations that communicate state (loading spinners, skeletons), which slow down instead of disappearing. Components get accessible motion for free. Locally-scoped "private" custom properties (`--_local-animation-*`) give the `.u-animate` utility family a clean composition API — modifiers only set variables; one declaration consumes them.

## 9 · Governance: making the system contributable

A design system is a product with internal users, so it ships with its own onboarding:

- **"Get Started / How to write stories"** — 8 MDX guides inside Storybook itself covering CSF3 vs MDX2, autodocs, Figma embeds, and a recommended story documentation structure (description → code usage → canvas → argTypes → Figma → best practices).
- **IA curated for two audiences**: `Introduction → Get Started → Foundations → Components`, with playground stories tagged out of autodocs so designers land on interactive pages and developers land on API tables.
- **Figma is linked, not duplicated** — `addon-designs` embeds the Figma source next to each story; the code remains the truth for values.
- **Quality gates**: `addon-a11y` on every story, Chromatic visual regression on the whole Storybook (TurboSnap: only changed stories are snapshotted), Stylelint budgets in CI.
- Even Storybook's own chrome is styled inside the system — an `8-trumps/storybook/` layer consumes the same tokens, so the docs site is itself a consumer of the design system (and dark mode works there too).

## 10 · Outcomes

- **One file per foundation is the entire token maintenance surface.** A palette change, a new easing curve or a spacing step is a single-file PR — apps, utilities, and Storybook documentation update from the same commit, with the docs *incapable* of drifting.
- **Nothing is hardcoded twice.** No token appears in a TS config, a Storybook constant, or a docs page by hand; every value shown anywhere is read from the live CSS.
- **The foundations became a daily tool.** Search-and-copy palettes and code-generating playgrounds turned the design system from reference material into part of the designer and developer workflow — including for the "which class do I use?" conversations that used to end in Slack.
- **Modern CSS replaced JavaScript** in measurable places: scroll listeners for table shadows, theme-switching logic, shade-generation scripts, and animation utility bookkeeping all became declarative CSS.
- **The system scaled across apps and themes** — two full themes resolved from one token graph, consumed by multiple applications in the monorepo, with brand-consistent runtime color generation (avatars) as a free side effect.
